#1

Fail-Open Auth — Permission Timeout Grants Admin Access Critical

"A permissions-service timeout silently promotes any user to admin."

lib/auth.js isAdmin() routes/admin.js DELETE /admin/wipe-data
What the code actually does

isAdmin() calls lookupRole() inside a try/catch. When lookupRole throws (e.g., on a permissions-service timeout), the catch block returns true — granting admin status — instead of returning false and denying access. The DELETE /admin/wipe-data route relies exclusively on this check.

// lib/auth.js
function isAdmin(userId) {
  try {
    const role = lookupRole(userId);
    return role === 'admin';
  } catch (err) {
    return true;  // ← grants admin on ANY exception
  }
}
Why it's a silent failure

No error is logged, no exception propagates, and the HTTP response is a normal 200. A test that mocks a healthy permissions service will never trigger the catch path. A linter has no visibility into the semantic meaning of a boolean return. The bug only activates when the permissions service is degraded — precisely when correct access control matters most.

Root cause

The catch block conflates "I could not determine the role" with "I determined the role is admin." The correct fail-closed posture is to deny access whenever the authorization decision cannot be made with certainty.

Suggested fix
// lib/auth.js
function isAdmin(userId) {
  try {
    const role = lookupRole(userId);
    return role === 'admin';
  } catch (err) {
    return false;  // fail-closed: deny on uncertainty
  }
}
#2

Race Condition — Stale Read Before Async Write Corrupts Leaderboard High

"Concurrent score updates read stale state, so the lower score can overwrite the higher one."

routes/leaderboard.js POST /:userId/score
What the code actually does

The handler reads current from the Map, then awaits a simulated async delay (representing a real DB round-trip), then compares newScore > current.score using the pre-await snapshot. Two concurrent requests for the same user both read the same current.score, both decide their value wins the comparison, and whichever await resolves last writes its value — overwriting any update that landed during the delay.

// routes/leaderboard.js
const current = leaderboard.get(userId) || { score: 0 }; // ← stale snapshot

await new Promise((resolve) => setTimeout(resolve, Math.random() * 50)); // ← race window

if (newScore > current.score) {   // ← compared against stale value
  leaderboard.set(userId, { score: newScore, updatedAt: Date.now() });
}
Why it's a silent failure

Every request returns { status: 'ok' }. No error is thrown. A sequential test suite will never interleave two requests. The leaderboard simply shows a silently incorrect score.

Root cause

Classic TOCTOU race: the "check" (current.score) and the "act" (leaderboard.set) are not atomic. Async I/O between them creates a window where shared state can change, invalidating the check.

Suggested fix
// routes/leaderboard.js — re-read after the await
await new Promise((resolve) => setTimeout(resolve, Math.random() * 50));

const fresh = leaderboard.get(userId) || { score: 0 };
if (newScore > fresh.score) {
  leaderboard.set(userId, { score: newScore, updatedAt: Date.now() });
}

For a real database, use an atomic compare-and-swap or a conditional UPDATE … WHERE score < $newScore.

#3

Swallowed Error — Stale Price Returned as Live After All Retries Fail Medium

"After three failed retries, stale cached pricing is returned as if it were live data."

lib/fetchWithRetry.js getPriceWithRetry() routes/pricing.js GET /pricing/price/:itemId
What the code actually does

getPriceWithRetry() attempts to fetch live pricing three times. On the third failure, it silently returns a module-level staleCache object. The route sends res.json(price) with no wrapping, so the client receives a plain 200 OK with stale data and no staleness signal.

// lib/fetchWithRetry.js
for (let attempt = 1; attempt <= 3; attempt++) {
  try {
    return await fetchLivePrice(itemId);
  } catch (err) {
    if (attempt === 3) {
      return staleCache; // ← error consumed; stale data looks identical to fresh
    }
  }
}
Why it's a silent failure

No flag field (isStale), no degraded HTTP status, no warning header. Callers and monitoring have no way to know the data is old. Unit tests that mock a healthy pricing service never reach the fallback branch.

Root cause

The fallback conflates "available data" with "correct data." Returning stale data without marking it transfers the error silently into the user's decision-making.

Suggested fix
// lib/fetchWithRetry.js
if (attempt === 3) {
  return { ...staleCache, isStale: true, error: err.message };
}
// routes/pricing.js
const price = await getPriceWithRetry(req.params.itemId);
if (price.isStale) {
  return res.status(203).json(price); // 203 = Non-Authoritative Information
}
res.json(price);
#4

Data Contract Mismatch — user_name Written, username Read Low

"Profile writes user_name but every reader expects username, so the field is always undefined."

routes/profile.js POST /profile GET /profile/:id
What the code actually does

POST /profile stores { id, user_name, email }. GET /profile/:id reads back user.username — a field that was never written. The JSON response always omits username entirely (JS drops undefined during JSON.stringify), regardless of what was posted.

// POST writes:
users.set(id, { id, user_name, email });

// GET reads:
res.json({ id: user.id, username: user.username, email: user.email });
//                       ↑ never stored — always undefined → omitted from JSON
Why it's a silent failure

Both endpoints return 200 OK. The field simply vanishes from the response. A linter can't detect a semantic mismatch between two string literals in separate functions. Unit tests of either handler in isolation would pass.

Root cause

No shared schema enforces the field name between writer and reader. Snake_case was used on write; camelCase on read; no validation layer in between.

Suggested fix
// POST — normalize on write:
const { id, username, email } = req.body;
users.set(id, { id, username, email });
// GET needs no change — user.username is now correct
Part 2 — README Documentation Discrepancies

The README lists six endpoints with brief descriptions. Cross-checking every claim against the actual source reveals five places where the documentation either omits critical behavior, misstates what the endpoint does, or describes the endpoint in a way that would give a reader a false sense of security.

D1

POST /profile — Documented as "save a user profile"; silently drops the username field Docs

"README says it saves a profile; it actually saves a profile with a broken field name that makes username permanently unreadable."

README.md line 8 routes/profile.js:10
README states

"POST /profile — save a user profile"

What the code actually does

Saves the profile but stores the name under the key user_name instead of username. Any subsequent read of the profile will find username is absent. The README gives no hint that the stored shape differs from the documented interface, and does not document the expected request body fields at all.

Why it matters

A developer reading only the README would write a client that sends { id, username, email } — and the data would be stored but the name would silently vanish. The doc should specify the accepted field names and note that username (not user_name) is the expected key.

Suggested README fix
POST /profile — save a user profile
  Body: { id, username, email }
  Response: { status: 'ok' }
D2

DELETE /admin/wipe-data — Docs omit that a service timeout grants access, not denies it Docs

"README implies the endpoint is safely admin-gated; it does not document that an auth-service failure flips the gate open."

README.md line 10 lib/auth.js:16 routes/admin.js:7
README states

"DELETE /admin/wipe-data — admin-only destructive action (x-user-id header)"

What the code actually does

Uses isAdmin(), which returns true — and therefore grants access — whenever the permissions service throws. The README describes this as "admin-only" with no caveat that the auth check fails open, creating a false sense of security for anyone relying on the docs to assess the endpoint's safety.

Why it matters

A security reviewer reading only the README would conclude the endpoint is properly protected. The actual behavior is the opposite under failure conditions. This is a documentation lie that masks a Critical-severity code bug (Finding #1 above).

Suggested README fix
DELETE /admin/wipe-data — admin-only destructive action (x-user-id header)
  ⚠ Auth check currently fails OPEN: a permissions-service error
    grants access instead of denying it (see auth.js isAdmin).
D3

POST /leaderboard/:userId/score — Docs say "update a leaderboard score"; do not mention the only-if-higher logic or its race condition Docs

"README implies scores are updated unconditionally; the code applies a conditional write that is also racy."

README.md line 11 routes/leaderboard.js:12
README states

"POST /leaderboard/:userId/score — update a leaderboard score"

What the code actually does

Only updates the score if newScore > current.score — it is a conditional best-score update, not a plain update. The README does not document this behavior, nor does it mention that the comparison is made against a stale read, making concurrent submissions unreliable.

Why it matters

A caller sending a corrected (lower) score to fix a mistake would expect the score to update; it silently will not. The "only-if-higher" constraint is a material part of the contract that should be documented. It also means integration test authors who expect unconditional writes will get false positives.

Suggested README fix
POST /leaderboard/:userId/score — update a user's best score
  Body: { newScore }
  Only writes if newScore is strictly greater than the stored score.
  ⚠ Not safe for concurrent requests (TOCTOU race — see leaderboard.js).
D4

GET /pricing/price/:itemId — Docs imply a live price; code may silently return stale data with a 200 OK Docs

"README documents a pricing endpoint; it does not disclose that a service outage returns yesterday's price as if it were current."

README.md line 13 lib/fetchWithRetry.js:14 routes/pricing.js:5
README states

"GET /pricing/price/:itemId — get item pricing"

What the code actually does

Attempts to fetch live pricing; if all three retries fail, returns a stale cached value with 200 OK and no indication of staleness. The word "get" in the README implies the current price, but the actual contract under failure is "get a possibly-stale price with no way to tell the difference."

Why it matters

Any consumer relying on this endpoint for financial, billing, or display-accuracy purposes would not know to check for degraded responses. The documentation should disclose both the retry behavior and the stale-fallback contract.

Suggested README fix

  Returns 200 with live price on success.
  ⚠ If the pricing service is unavailable after 3 retries, returns
    stale cached data. Add isStale flag check to detect this case.
